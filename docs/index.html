Talk to any NPC.

An interruptible voice NPC for Unity, built to sit inside your FMOD mix. No recording budget.

We help Unity game developers give NPCs real, interruptible voice conversations without a recording budget, through one FMOD-native character asset, so players can talk to any NPC and get an in-character answer inside the game's own mix.

The FMOD programmer-instrument sink is live and verified: hold a key, walk up to an NPC, and talk — speech recognition, the reply and the voice all run on your own GPU.

Why NPCs

Design the character once: who it is, what it knows, what it never says. It ships as one asset dropped onto a Unity NPC, and the player talks to it inside the game's own mix.

Recording does not scale

The SAG-AFTRA floor is $1,134.95 for a 4-hour day covering up to three voices, before studio, direction and retakes. Skyrim shipped around 60,000 lines; Starfield was announced at over 250,000. Nobody records an open world twice.

An AI voice has to be an ordinary voice

Same FMOD buses, attenuation curves, occlusion, reverb sends and ducking the sound designer already built. Anything else means a second mix, and that is where AI dialogue starts to sound pasted on.

Cost per player is a budget, not a hope

The runtime enforces a spending ceiling the same way it enforces latency. Out of budget means an authored line, never an error dialog.

This already ships. PUBG's Ally Duo runs a quantized 2B Mistral-NeMo-Minitron on the player's GPU; inZOI's Smart Zoi runs a 0.5B Minitron. VoiceRT uses the same split: reflexes never wait for the model.

The character stays inside the game's lore, and the guardrail is structural: the NPC has no tools outside the game engine to reach for. The whole argument with numbers: docs/economics.md.

How it works

Everything heavy (VAD, STT, the LLM, TTS) stays in the Python process, on your own GPU. The engine gets a few hundred lines of C#: one socket per live NPC, PCM queued into an ordinary engine sound, text and tool calls forwarded to your MonoBehaviour. The engine never runs a model.

  1. Push-to-talk mic: hold to capture, release sends ENDPOINT — that starts generation
  2. Dialogue LOD opens the socket only for a LIVE NPC
  3. EnergyVAD: drives barge-in, does not close a held-key turn
  4. STT: Whisper small.en, whole utterance
  5. LLM: qwen3:8b via Ollama, lore-locked, engine-only tools
  6. TTS: Kokoro to PCM16
  7. FMOD programmer instrument
  8. Game mix: 3D, occlusion, ducking, buses

All three stages must resolve to CUDA or the server refuses to start. Barge-in cancels everything in flight and sends FLUSH.

Unreal + Wwise is the same picture with UAkAudioInputComponent in the FMOD slot.

The NPC contract

Transportengine bridge: one TCP socket per live NPC, PCM16 16 kHz in both directions
System promptstrict lore rules. The character knows nothing of the real world, speaks in one or two sentences, and answers attempts to break character in character
Toolsemit_game_event · query_world_state · play_animation. Engine only, and the isolation is structural
Barge-in gate0 ms. Cuts instantly, because game feel beats politeness
Turn boundarya client that ends its own utterances (push-to-talk) owns the boundary; the VAD still opens capture and still drives barge-in, but only the key closes a turn — a pause mid-sentence is not the end of one
Interrupted replydropped: cleaner lore, shorter prompt, lower latency
Latency budgetfrom end of player speech: first LLM token ≤ 150 ms · first audio ≤ 300 ms
Memoryone JSON file per (NPC, player), read before the reply and written after — the character recognizes a returning player without being told
Local stackWhisper small.en · qwen3:8b via Ollama · Kokoro. The server checks all three resolved to CUDA at boot and refuses to start on a CPU fallback

voicert · session — profile npc

1 · Frames, not callbacks

Everything moving through the system is an immutable frame: AudioFrame, TextFrame, FunctionCallFrame, InterruptionFrame. The processors (STT, LLM, TTS) talk only in frames, so changing a provider never touches the core.

2 · What happens when the player interrupts

The VAD hears the player, and everything in flight is cancelled at its next await point: LLM generation, TTS synthesis, the queues in between, and a FLUSH to the engine so nothing produced before the cut plays after it. The history keeps only the characters that were actually voiced, so the NPC never remembers words the player never heard.

3 · The tool set is closed

emit_game_event, query_world_state, play_animation and nothing else. A prompt injection asking for a tool outside the engine hits PermissionError: there is nothing outside the game to reach. The 0 ms gate, the VAD sensitivity and the drop-on-interrupt context policy are part of the same contract.

The automated test suite runs on deterministic stubs, so CI needs no API keys and no GPU: 50 ms to first audio on stubs, 228 tests, mypy strict on 33 files. The Unity demo itself runs the real local stack — Whisper, qwen3:8b, Kokoro — because that is the point of the pipeline. Switching either path to a different provider is an adapter, not a rebuild. Internals: docs/architecture.md.

Wiring into FMOD

The rule is simple: an AI voice has to be an ordinary voice. Same buses, attenuation, occlusion, reverb sends, ducking and voice limiting the sound designer already set up. Anything else means keeping a second mix alive, and that is where AI dialogue starts to sound pasted on.

UNITY + FMOD

Use a user-created sound. Call createSound with FMOD_OPENUSER and an FMOD_CREATESOUNDEXINFO (defaultfrequency, numchannels, format, pcmreadcallback). FMOD then pulls PCM in decodebuffersize blocks.

  • pass it to a programmer instrument via CREATE_PROGRAMMER_SOUND, release on DESTROY
  • it inherits the event's 3D panning, buses and effects
  • concurrency is already handled: maxchannels 256–1024 virtual · softwareChannels 64 real
  • status: shipped — compiled and verified live in Unity 6.3 LTS with FMOD for Unity 2.03.14
UNITY · PLAIN AUDIOSOURCE

No middleware? The package streams into an ordinary AudioSource through OnAudioFilterRead or PCMReaderCallback. The sink contract is two methods, push(pcm, sample_rate) and flush(), so the native shim is straightforward. flush() is the barge-in path and has to drop queued audio immediately, or the NPC carries on talking after the player cut them off.

  • Add Component > VoiceRT > VoiceRT NPC; it requires an AudioSource, so Unity adds one
  • VoiceRT Dialogue LOD opens and closes the socket as the player crosses the LIVE distance
  • status: wire protocol and PCM ring buffer verified against a live bridge from C# (13 xUnit tests, including a full turn plus a barge-in over a real socket); compiled and running end to end, including a Windows player build
UNREAL + WWISE

Use the stock Audio Input source plug-in. Register three global callbacks once with SetAudioInputCallbacks(). The engine calls the format callback when playback starts, then the execute callback on every audio frame until you stop it or return AK_NoMoreData. Without middleware, use USoundWaveProcedural::QueueAudio.

  • subclass UAkAudioInputComponent, override FillSamplesBuffer + GetChannelConfig
  • start it with Post Associated Audio Input Event; a plain PostEvent will not work
  • already proven: ReadSpeaker speechEngine, 4Players ODIN, Unreal AudioLink
  • status: protocol verified in standalone C++; Editor glue not exercised

The Unity component is compiled and running against the real engine: a Windows player build that starts its own local server and holds a full voice conversation with an NPC through a real microphone. The Unreal component is not — protocol and PCM ring buffer verified against a live voicert.game.bridge process from standalone C++, but the engine-specific glue has not been exercised inside an Editor. Treat Unreal as a working prototype to drop in and iterate on, not a marketplace-ready asset yet. Wiring for both middlewares, FMOD first: docs/middleware-wiring.md.

Dialogue LOD: you pay for what the player can hear

Nobody renders every blade of grass at full detail. Dialogue works the same way here. Only the NPC you are actually talking to runs the full pipeline.

LIVEone pool slot

Full pipeline: STT → LLM → TTS, streamed. The NPC in front of you.

BARKno pool slot · one short LLM call

The LLM picks a line from a bank you already shipped instead of making one. No synthesis and no new asset, just one short call to choose which line fits.

CROWD~0 · one shared bed

Ambient murmur. No per-NPC agent exists at all.

OFF0

Out of earshot. Nothing runs, NPC state frozen.

python examples/game_open_world.py — 240 NPCs, market square 
DIALOGUE LOD    (240 NPCs in the square)
  LIVE      2 NPC   full STT+LLM+TTS, one pool slot each
  BARK      4 NPC   LLM picks a pre-baked line — no synthesis
  CROWD    53 NPC   one shared murmur bed
  OFF     181 NPC   nothing runs

PLAYER WALKS 40 m ACROSS THE SQUARE
  step 1: live=  2  bark= 13  crowd= 63  off=162  | agents held: 2
  step 3: live= 15  bark= 36  crowd= 68  off=121  | agents held: 7
  step 4: live= 32  bark= 43  crowd= 68  off= 97  | agents held: 7  ← capped

live= is how many NPCs qualify for the LIVE tier; agents held: is how many got a pool slot. Live agents come out of a fixed-size pool, and when it is full the lowest-priority one is dropped. FMOD and Wwise already limit voices the same way. A quest-giver outranks an ambient vendor, and anything dropped falls back to the bark tier instead of going silent. 240 NPCs in the world, never more than 7 agents in memory.

It stays out of the frame budget

16.6 ms stays untouched, by design

Synthesis runs off the render thread, so the 16.6 ms frame at 60 fps is untouched by design and what limits you is a fraction of one CPU core, not frame time. The measure is the real-time factor: seconds of CPU per second of audio, so below 1.0 is faster than real time. On a Raspberry Pi 4, Piper voices measured RTF 0.77–0.81 on one thread and 0.35 on four. If a Pi can synthesize faster than real time, a gaming PC is not the bottleneck. Supertonic reports RTF 0.012–0.015 on an M4 Pro CPU.

Pool size is calculated, not guessed

Give the budget a real-time factor and a CPU allowance and it tells you how many voices you can run at once. Measure it on your minimum spec, not on your workstation.

ComputeBudget(
  rtf=0.10,
  cpu_share=0.35,
  speaking_duty=0.5,
).max_pool_size()   # → 7

Already shipping in games

PUBG's Ally Duo runs a quantized 2B Mistral-NeMo-Minitron entirely on-device (an RTX GPU with at least 8 GB of VRAM, shared with the game). Its System-1 behaviour tree acts at tick rate while the System-2 model reasons separately, so reflexes never wait for the model. VoiceRT uses the same split. inZOI's Smart Zoi runs a 0.5B Minitron.

Bake what you can, generate what you cannot

stagebuild time (baked)player's devicecloud
Static dialogue yes, best quality, paid once——
Reactive barks —yes, local TTS · $0 per player—
Open conversation —yes, small local LLM + local TTS optional, big moments only

Baking is the default for a reason. Cloud TTS costs $4–$30 per 1M characters (Google Standard $4 / Neural2 $16 / Chirp 3 HD $30; Polly Standard $4 / Neural $16 / Generative $30), so a 10,000-line bank is a rounding error and re-baking it after a script change costs nothing. On phones the local LLM path already works: Gemma 3 1B is 529 MB at int4 QAT (about 2,585 tok/s prefill on a Galaxy S24 Ultra), and Apple's roughly 3B on-device model runs at about 30 tok/s on an iPhone 15 Pro, free to developers. Local TTS on a phone is the open question below.

Local TTS is the lever

Speech synthesis is about 90% of a cloud voice turn; the language model is under 2%. Swapping to a cheaper LLM optimizes a rounding error. Local TTS is the 10× lever, and it is tractable where a local LLM is not: a Piper-class voice is ~60 MB of CPU-only inference. At $10 net per player and a 90% margin target, all-cloud funds 652 turns; moving only synthesis on-device funds 6,587.

Every stage already has a local option

  • VAD: EnergyVAD ships today; Silero is designed, not yet wired
  • STT: faster-whisper on GPU/NPU
  • LLM: llama.cpp-class on-device models
  • TTS: Piper / Kokoro on desktop; the phone target still needs a benchmark (see licensing)
  • memory: sqlite-vec, a vector database in one file

The ceiling is enforced at runtime

BudgetDenied carries an affordable authored fallback, reserve-then-settle holds under concurrency, and barge-in stops the meter. Any cloud stage can be swapped for an on-device one through the same adapter interface of about 50 lines. All of it, with the caveats: docs/economics.md. The fully offline path, measured: docs/local-stack.md.

Engine wiring, FMOD first: see Wiring into FMOD above.

LICENSING WILL BITE YOU BEFORE PERFORMANCE DOES
  • Piper now lives at piper1-gpl and is GPL-3.0. It embeds espeak-ng, which is GPL, so linking against it makes your binary a derived work. Dynamic linking does not avoid that, and pinning the old MIT code does not help either: its CMake still links GPL espeak-ng. Running Piper as a separate process still ships a GPL binary alongside your game, so talk to a lawyer, and GPLv3 Installation Information is a real problem on locked consoles. An MIT fork with an espeak-free G2P, such as ayutaz/piper-plus, is the other route.
  • Voice models are licensed separately from the engine. en_US-lessac, the voice in Piper's own examples, is under the restrictive Blizzard 2013 license. Read the MODEL_CARD of every voice you ship.
  • Kokoro-82M is Apache-2.0, weights included. Clean licensing, but it measured RTF 2.77–6.63 on a Raspberry Pi 4, so it is not real time on low-power ARM. Fine on desktop; benchmark it before committing a handheld target.
  • sherpa-onnx (Apache-2.0) is the easiest runtime to ship: Windows, Linux, macOS, Android and iOS, no network needed. It still pulls in GPL espeak-ng through piper-phonemize, though there is an open upstream issue to remove it.

None of this stops you shipping. It means choosing the stack with a lawyer in the room. And because every provider sits behind the same adapter interface, changing that choice later is a swap rather than a rewrite. The full picture: docs/licensing.md.
