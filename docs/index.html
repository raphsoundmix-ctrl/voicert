How it works in real time

A scripted run of the real loop, with the same stages and the same metrics that voicert.metrics writes to the logs. Interruption included.

voicert · session — profile assistant 
press "Run session"...

1 · Frames, not callbacks

Everything moving through the system is an immutable frame: AudioFrame, TextFrame, FunctionCallFrame, InterruptionFrame. The processors (STT, LLM, TTS) talk only in frames, so changing a provider never touches the core.

2 · What happens when you interrupt

The local VAD hears you, running asyncio tasks are cancelled, the queues are drained, and the transport flushes playback. The history then keeps only the part that was actually spoken aloud, so the agent never remembers words you never heard.

3 · A profile is a contract

Sales, assistant and NPC differ in structure, not wording. Each has its own set of tools that does not overlap with the others, so an NPC cannot reach the CRM even under prompt injection. Each also has its own latency budget, VAD sensitivity and context policy.

Models: interfaces now, providers later

The core does not know which vendor is behind a stage. Every provider is an adapter of about 50 lines against a stable interface (STTService / LLMService / TTSService). Right now the pipeline runs on deterministic stubs, so the tests and the demo need no API keys.

STT · speech to text
  • Deepgram Nova-3 — websocket streaming, ~150 ms interim results primary
  • faster-whisper — local GPU inference, offline fallback, no key required
LLM · reasoning & tools
  • Claude Haiku — NPC: speed wins primary for NPC
  • Claude Sonnet — Sales/Assistant: reasoning quality
  • OpenRouter — any model behind one key, for experimentation
TTS · text to speech
  • ElevenLabs Flash v2.5 — ≈75 ms TTFB primary for NPC
  • Cartesia Sonic — stable prosody over long sessions

ConfigFactory decides which model each profile gets: the fastest for NPC, the most accurate for sales.

Where it applies

📞

Sales Agent

Inbound and outbound calls over SIP or Twilio. Follows a scripted conversation graph, qualifies the lead, logs objections to the CRM, and holds the deal context for the whole call.

  • transport: SIP / Twilio Media Streams
  • tools: crm_lookup · crm_update_deal · crm_log_objection · schedule_callback · transfer_to_human
  • interrupt gate 250 ms, so an "uh-huh" does not kill the pitch
  • interrupted reply is kept and marked: an interruption usually means an objection

Personal Assistant

Jarvis-style, for conferences, meetings and everyday tasks. It remembers its owner over time, searches the web, handles the calendar, controls IoT devices and opens apps. All by voice, over WebRTC, from any device.

  • transport: WebRTC (Opus 48k)
  • tools: web_search · calendar_create · memory_store/recall · iot_command · os_open_app
  • interrupt gate 120 ms
  • anything irreversible needs a spoken confirmation first
First audio out
800 ms
🎮

In-Game NPC

A character that stays inside the game's lore. The guardrail is structural: the NPC has no tools outside the game engine to reach for. It reacts to in-game events over WebSocket or gRPC, with gestures timed to speech.

  • transport: WebRTC + WebSocket/gRPC to the engine
  • tools: emit_game_event · query_world_state · play_animation, and nothing else
  • interrupt gate 0 ms, because game feel comes first
  • interrupted reply is dropped: cleaner lore, shorter prompt

Voicing an open world: what it costs

Two questions come first for any game developer. What does it cost to run, and does it pay for itself? Both have numbers below, and the voicert.game module implements the answer.

NPCs are the focus. VoiceRT was selected for AltaLab, the accelerator run by the AltaIR Capital fund; the Fall 2026 cohort is where this gets built with their support. The goal is one complete solution: design a character once, package it as a single engine asset with its voice and boundaries, drop it onto any NPC in Unity or Unreal, and talk to it. The audio side is built with 14+ years of technical sound design and FMOD across PC, console and mobile.

$1,135 SAG-AFTRA minimum for a 4-hour session, up to 3 voices (IMA 2025–26). Before studio, direction and editing. You pay it again after every rewrite.
250k+ lines of dialogue announced for Starfield (Bethesda pre-release count). Skyrim ~60k, Fallout 4 111k. No indie studio can buy that.
$0 what one extra line costs when it is synthesized on the player's device. The cost does not grow with units sold.

Dialogue LOD: you pay for what the player can hear

Nobody renders every blade of grass at full detail. Dialogue works the same way here. Only the NPC you are actually talking to runs the full pipeline.

LIVEone pool slot

Full pipeline: STT → LLM → TTS, streamed. The NPC in front of you.

BARKno pool slot · one short LLM call

The LLM picks a line from a bank you already shipped instead of making one. No synthesis and no new asset, just one short call to choose which line fits.

CROWD~0 · one shared bed

Ambient murmur. No per-NPC agent exists at all.

OFF0

Out of earshot. Nothing runs, NPC state frozen.

python examples/game_open_world.py — 240 NPCs, market square 
DIALOGUE LOD    (240 NPCs in the square)
  LIVE      2 NPC   full STT+LLM+TTS, one pool slot each
  BARK      4 NPC   LLM picks a pre-baked line — no synthesis
  CROWD    53 NPC   one shared murmur bed
  OFF     181 NPC   nothing runs

PLAYER WALKS 40 m ACROSS THE SQUARE
  step 1: live=  2  bark= 13  crowd= 63  off=162  | agents held: 2
  step 3: live= 15  bark= 36  crowd= 68  off=121  | agents held: 7
  step 4: live= 32  bark= 43  crowd= 68  off= 97  | agents held: 7  ← capped

Live agents come out of a fixed-size pool, and when it is full the lowest-priority one is dropped. Wwise and FMOD already limit voices the same way. A quest-giver outranks an ambient vendor, and anything dropped falls back to the bark tier instead of going silent. 240 NPCs in the world, never more than 7 agents in memory.

It stays out of the frame budget

16.6 ms stays untouched

Synthesis runs off the render thread, so what limits you is a fraction of one CPU core, not frame time. The measure is the real-time factor: seconds of CPU per second of audio, so below 1.0 is faster than real time. On a Raspberry Pi 4, Piper voices measured RTF 0.77–0.81 on one thread and 0.35 on four. If a Pi can synthesize faster than real time, a gaming PC is not the bottleneck. Supertonic reports RTF 0.012–0.015 on an M4 Pro CPU.

Pool size is calculated, not guessed

Give the budget a real-time factor and a CPU allowance and it tells you how many voices you can run at once. Measure it on your minimum spec, not on your workstation.

ComputeBudget(
  rtf=0.10,
  cpu_share=0.35,
  speaking_duty=0.5,
).max_pool_size()   # → 7

Already shipping in games

PUBG's Ally Duo runs a quantized 2B Mistral-NeMo-Minitron entirely on-device (an RTX GPU with at least 8 GB of VRAM, shared with the game). Its System-1 behaviour tree acts at tick rate while the System-2 model reasons separately, so reflexes never wait for the model. VoiceRT uses the same split. inZOI's Smart Zoi runs a 0.5B Minitron.

Baking is the default for a reason. Cloud TTS costs $4–$30 per 1M characters (Google Standard $4 / Neural2 $16 / Chirp 3 HD $30; Polly Standard $4 / Neural $16 / Generative $30), so a 10,000-line bank is a rounding error and re-baking it after a script change costs nothing. On phones the local path already works: Gemma 3 1B is 529 MB at int4 QAT (about 2,585 tok/s prefill on a Galaxy S24 Ultra), and Apple's roughly 3B on-device model runs at about 30 tok/s on an iPhone 15 Pro, free to developers.

Wiring into Wwise and FMOD

The rule is simple: an AI voice has to be an ordinary voice. Same buses, attenuation, occlusion, reverb sends, ducking and voice limiting the sound designer already set up. Anything else means keeping a second mix alive, and that is where AI dialogue starts to sound pasted on.

WWISE

Use the stock Audio Input source plug-in. Register three global callbacks once with SetAudioInputCallbacks(). The engine calls the format callback when playback starts, then the execute callback on every audio frame until you stop it or return AK_NoMoreData.

  • Unreal: subclass UAkAudioInputComponent, override FillSamplesBuffer + GetChannelConfig
  • start it with Post Associated Audio Input Event; a plain PostEvent will not work
  • already proven: ReadSpeaker speechEngine, 4Players ODIN, Unreal AudioLink
FMOD

Use a user-created sound. Call createSound with FMOD_OPENUSER and an FMOD_CREATESOUNDEXINFO (defaultfrequency, numchannels, format, pcmreadcallback). FMOD then pulls PCM in decodebuffersize blocks.

  • pass it to a programmer instrument via CREATE_PROGRAMMER_SOUND, release on DESTROY
  • it inherits the event's 3D panning, buses and effects
  • concurrency is already handled: maxchannels 256–1024 virtual · softwareChannels 64 real

No middleware? Use Unity's OnAudioFilterRead or PCMReaderCallback, or Unreal's USoundWaveProcedural::QueueAudio. The sink contract here is two methods, push(pcm, sample_rate) and flush(), so the native shim is straightforward. flush() is the barge-in path and has to drop queued audio immediately, or the NPC carries on talking after the player cut them off.

LICENSING WILL BITE YOU BEFORE PERFORMANCE DOES
  • Piper now lives at piper1-gpl and is GPL-3.0. The MIT rhasspy/piper was archived read-only on 2025-10-06. Piper embeds espeak-ng, which is GPL, so linking against it makes your binary a derived work that has to ship under GPL-3.0 as well. Dynamic linking does not avoid that, and pinning the old MIT code does not help either: its CMake still links GPL espeak-ng.

    Two routes work. Run Piper as a separate process, though you still ship a GPL binary alongside your game, so talk to a lawyer, and GPLv3 Installation Information is a real problem on locked consoles. Or use an MIT fork with an espeak-free G2P, such as ayutaz/piper-plus.
  • Voice models are licensed separately from the engine. en_US-lessac, the voice in Piper's own examples, is under the restrictive Blizzard 2013 license. Read the MODEL_CARD of every voice you ship.
  • Kokoro-82M is Apache-2.0, weights included (8 languages, 54 voices, 86–326 MB of ONNX). Clean licensing, but it measured RTF 2.77–6.63 on a Raspberry Pi 4, so it is not real time on low-power ARM. Fine on desktop; benchmark it before committing a handheld target.
  • sherpa-onnx (Apache-2.0) is the easiest runtime to ship: Windows, Linux, macOS, Android and iOS, on x86, ARM and RISC-V, 12 bindings, no network needed. It still pulls in GPL espeak-ng through piper-phonemize, though there is an open upstream issue to remove it.

None of this stops you shipping. It means choosing the stack with a lawyer in the room. And because every provider sits behind the same adapter interface, changing that choice later is a swap rather than a rewrite.

Where this is going

The pipeline does not know which vendor is behind a stage. Any cloud stage can be swapped for an on-device one through the same adapter interface of about 50 lines, and the core has no dependencies to get in the way.

NPC character asset (cohort focus)

The game's audio middleware becomes the transport. Wwise or FMOD sends the player's voice into VoiceRT, and the NPC answers through the game's own audio bus, in character and inside the lore, with no dialogue trees and no scripted lines. The AltaLab Fall 2026 cohort goal: ship this as one asset a studio drops onto a character.

  • design once: who it is, what it knows, what it never says
  • one asset: persona + voice + boundaries, dropped onto Unity / Unreal NPCs
  • 0 ms interrupt gate, so a player can talk over an NPC and it reacts like a person
🌍

Multilingual by design

A language is a setting, not a port. The profile carries the prompt and the voice, and every planned provider is already multilingual.

  • Whisper: 99 languages, runs locally
  • ElevenLabs / Cartesia: multilingual voices behind one API
  • VAD and barge-in do not care about language: they hear energy and speech, not words
  • context policies and tool isolation work the same in any locale
📱

Fully local, fully private

The goal is an assistant for a business owner where the knowledge base lives on the phone and both the reasoning and the voice run on the device, offline. Every stage of the pipeline already has a local option.

  • VAD: Silero, already designed to run local in this repo
  • STT: faster-whisper on GPU/NPU
  • LLM: llama.cpp-class on-device models
  • TTS: Piper / Kokoro on desktop; the phone target still needs a benchmark (see licensing)
  • memory: sqlite-vec, a vector database in one file

The demo you just ran uses stub providers through the same interfaces a real local or cloud model would use. 51 tests pass through those seams, so switching to a real model is an adapter, not a rebuild.

A NOTE FROM THE AUTHOR

This is a working prototype. I am still building on it. I have worked with sound and voice for more than ten years, and that is where the design comes from: I know what processing belongs at each point of the chain, what is worth automating, and how it has to behave on a server.

What I want is one agent that can be configured for almost any job. It should run locally, speak several languages, and be simple to plug into whatever you already have: a stable frame contract and adapters of about 50 lines. A fully local knowledge base is the next step.

In games it connects to Wwise or FMOD. The engine sends the player's voice to the NPC, and the NPC answers inside the game world with no dialogue script behind it. The use I care about most is a personal assistant for a business owner, where the database, the reasoning and the voice all end up on the phone and work without internet. Given a database, prepared prompts and a voice, that is an engineering plan rather than a wish.
