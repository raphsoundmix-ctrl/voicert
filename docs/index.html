How it works in real time

1 · Frames, not callbacks

Everything that moves through the system is an immutable frame: AudioFrame, TextFrame, FunctionCallFrame, InterruptionFrame. Processors (STT → LLM → TTS) communicate exclusively through frames, so swapping a provider never touches the core.

2 · Barge-in as physics, not a feature

The local VAD detects speech → in-flight asyncio generation tasks are cancelled → queues are drained → the transport flushes playback. And the dialogue history keeps only the actually spoken prefix of the reply — the agent never “remembers” words the user never heard.

3 · A profile is a contract

Sales, Assistant, and NPC differ structurally: tool registries are physically isolated (an NPC cannot invoke the CRM even under prompt injection), and each profile carries its own latency budget, VAD sensitivity, and context policy.

Models: plugged in later, interfaces ready now

The core is vendor-agnostic. Every provider is a ~50-line adapter against a stable interface (STTService / LLMService / TTSService). Today the pipeline runs on deterministic stubs — the tests and the demo require no API keys at all.

STT · speech to text
  • Deepgram Nova-3 — websocket streaming, ~150 ms interim results primary
  • faster-whisper — local GPU inference, offline fallback, no key required
LLM · reasoning & tools
  • Claude Haiku — NPC: speed wins primary for NPC
  • Claude Sonnet — Sales/Assistant: reasoning quality
  • OpenRouter — any model behind one key, for experimentation
TTS · text to speech
  • ElevenLabs Flash v2.5 — ≈75 ms TTFB primary for NPC
  • Cartesia Sonic — stable prosody over long sessions

Model-to-profile routing lives in the ConfigFactory: NPC gets the fastest models, Sales gets the most accurate ones.

Inbound and outbound calls over SIP/Twilio. A scripted conversation graph, lead qualification, objection handling logged to the CRM, and deal context maintained across the entire call.

Personal Assistant

Jarvis-style: conferences, meetings, everyday tasks. Long-term memory about its principal, web search, calendar, IoT, and application control — by voice, over WebRTC, from any device.

  • transport: WebRTC (Opus 48k)
  • tools: web_search · calendar_create · memory_store/recall · iot_command · os_open_app

In-Game NPC

A character that lives strictly within the game's lore. The guardrails are structural: the NPC physically has no tools outside the game engine. It reacts to in-game events over WebSocket/gRPC, with gestures synchronized to speech.

  • transport: WebRTC + WebSocket/gRPC to the engine
  • tools: emit_game_event · query_world_state · play_animation — nothing else
  • barge-in: instant (0 ms) — game feel first
  • interrupted reply is dropped from context: cleaner lore, shorter prompt

Voicing an open world — the indie economics

Developers ask two questions before the interesting ones: what does it cost to run, and does it pay for itself? Here are both answers, with sourced numbers — and the voicert.game module that implements them.

$1,135 SAG-AFTRA minimum per 4-hour session, up to 3 voices (IMA 2025–26). Before studio, direction, editing — and again after every rewrite.
250k+ lines of dialogue announced for Starfield (Bethesda pre-release count). Skyrim ~60k, Fallout 4 111k. No indie buys that.
$0 marginal cost of a line synthesized on the player's device. It does not scale with units sold. That is the whole unlock.

Dialogue LOD — cost scales with what the player can hear

Nobody renders every blade of grass at full resolution. Dialogue gets the same treatment: only the NPC you are actually talking to runs the full pipeline.

LIVEone pool slot

Full pipeline: STT → LLM → TTS, streamed. The NPC in front of you.

BARK~0 · asset playback

The LLM selects a pre-baked line instead of synthesizing one. Audible, in character, free.

CROWD~0 · one shared bed

Ambient murmur. No per-NPC agent exists at all.

OFF0

Out of earshot. Nothing runs, NPC state frozen.

python examples/game_open_world.py — 240 NPCs, market square

  BARK      4 NPC   LLM picks a pre-baked line — no synthesis
  CROWD    53 NPC   one shared murmur bed

  step 1: live=  2  bark= 13  crowd= 63  off=162  | agents held: 2
  step 3: live= 15  bark= 36  crowd= 68  off=121  | agents held: 7
  step 4: live= 32  bark= 43  crowd= 68  off= 97  | agents held: 7  ← capped

Live agents are a bounded, priority-evicted pool — the same discipline Wwise and FMOD already apply to voices. A quest-giver outranks an ambient vendor; anyone evicted degrades to the bark tier rather than falling silent. 240 NPCs in the world, never more than 7 agents in memory.

It never touches the frame budget

16.6 ms is untouchable

Synthesis runs off the render thread, so the constraint is a fraction of one CPU core, not frame time. Measured on a Raspberry Pi 4, Piper voices hit RTF 0.77–0.81 on one thread and 0.35 on four. If a Pi synthesizes faster than real time, a gaming PC is not the bottleneck. Supertonic reports RTF 0.012–0.015 on an M4 Pro CPU.

Pool size is derived, not guessed

Give the budget a real-time factor and a CPU allowance, and it returns the number of concurrent voices you can afford — measured on your minimum spec, not your workstation.

ComputeBudget(
  rtf=0.10,
  cpu_share=0.35,
  speaking_duty=0.5,
).max_pool_size()   # → 7

Already shipping in games

PUBG's Ally Duo runs a quantized 2B Mistral-NeMo-Minitron fully on-device (RTX, ≥8 GB VRAM shared with the game). Its System-1 behaviour tree acts at tick rate while the System-2 model reasons separately — reflexes never wait for the model. Same split here. inZOI's Smart Zoi uses a 0.5B Minitron.

Hybrid by design — bake what you can, generate what you can't

Baking is the default on purpose: commodity cloud TTS runs $4–$30 per 1M characters (Google Standard $4 / Neural2 $16 / Chirp 3 HD $30; Polly Standard $4 / Neural $16 / Generative $30), so a 10,000-line bank is a rounding error and re-bakes free when the script changes. On mobile the local path is real today: Gemma 3 1B is 529 MB at int4 QAT (~2,585 tok/s prefill on a Galaxy S24 Ultra), and Apple's ~3B on-device model runs ~30 tok/s on an iPhone 15 Pro, free to developers.

Wiring into Wwise and FMOD

The rule: an AI voice must be an ordinary voice — same buses, attenuation, occlusion, reverb sends, ducking, and voice limiting the sound designer already authored. Anything else means a second mix to maintain, and that is where AI dialogue starts sounding pasted-on.

WWISE

Stock Audio Input source plug-in. Register three global callbacks once via SetAudioInputCallbacks(): the engine calls the format callback at the start of playback and the execute callback every audio frame until stop or AK_NoMoreData.

  • Unreal: subclass UAkAudioInputComponent, override FillSamplesBuffer + GetChannelConfig
  • start with Post Associated Audio Input Event — a plain PostEvent will not drive it
  • proven transport: ReadSpeaker speechEngine, 4Players ODIN, Unreal AudioLink
FMOD

A user-created sound: createSound with FMOD_OPENUSER + FMOD_CREATESOUNDEXINFO (defaultfrequency, numchannels, format, pcmreadcallback). FMOD pulls PCM in decodebuffersize blocks.

  • hand it to a programmer instrument via CREATE_PROGRAMMER_SOUND, release on DESTROY
  • inherits the event's 3D panning, buses and effects
  • concurrency already solved: maxchannels 256–1024 virtual · softwareChannels 64 real

No middleware? Unity's OnAudioFilterRead / PCMReaderCallback, Unreal's USoundWaveProcedural::QueueAudio. The framework's sink contract is two methods — push(pcm, sample_rate) and flush() — so the native shim is mechanical. flush() is the barge-in path: it must drop queued audio instantly, or the NPC keeps talking after the player cut them off.

⚠ LICENSING IS THE REAL TRAP — NOT PERFORMANCE
  • Piper moved to piper1-gpl, which is GPL-3.0 (the MIT rhasspy/piper was archived read-only, 2025-10-06). It embeds espeak-ng, so it blocks any linking — dynamic included. Pinning the old MIT code does not help: its CMake still links GPL espeak-ng. Routes that work: run it out-of-process (you still convey a GPL binary — take counsel, and GPLv3 Installation Information is a real problem on locked consoles), or use an MIT fork with espeak-free G2P such as ayutaz/piper-plus.
  • Voice models carry their own licenses, separately from the engine — and en_US-lessac, the voice in Piper's own examples, sits under the restrictive Blizzard 2013 license. Check every MODEL_CARD you ship.
  • Kokoro-82M is Apache-2.0 including weights (8 languages, 54 voices, 86–326 MB ONNX) — clean, but it measured RTF 2.77–6.63 on a Raspberry Pi 4: not real-time on low-power ARM. Fine on desktop; benchmark before betting a handheld target on it.
  • sherpa-onnx (Apache-2.0) is the most shippable runtime — Windows/Linux/macOS/Android/iOS, x86/ARM/RISC-V, 12 bindings, fully offline — but today still pulls GPL espeak-ng via piper-phonemize (upstream issue open to strip it).

None of this blocks shipping. It means picking the stack with a lawyer in the room — and because every provider sits behind the same adapter contract, that choice is a swap, not a rewrite.

Where this is going — and why it will work

Every claim below is backed by the architecture in this repository. The pipeline is provider-agnostic by construction: any cloud stage swaps for an on-device counterpart through the same ~50-line adapter contract, and the core itself has zero dependencies to get in the way.

🎮

Wwise / FMOD NPC bridge

Game audio middleware becomes the transport: Wwise or FMOD routes the player's voice bus to VoiceRT, and the NPC answers through the game's own audio bus — in character, inside the lore, with no dialogue trees and no scripted lines.

  • engine link is already event-driven (WebSocket/gRPC) in the NPC profile
  • middleware handles mixing/spatialization — VoiceRT handles listening, thinking, speaking
  • 0 ms barge-in gate: the player talks over the NPC and it reacts like a person
🌍

Multilingual by design

A language is a configuration, not a rewrite: the profile carries the prompt and the voice, and every planned provider is natively multilingual.

  • Whisper: 99 languages, runs locally
  • ElevenLabs / Cartesia: multilingual voices, one API
  • VAD and barge-in are language-independent — they hear energy and speech, not words
  • context policies and the tool firewall are locale-agnostic by design
📱

Fully local, fully private

The endgame: a business owner's assistant where the entire knowledge base lives on the phone, and reasoning plus speech synthesis run on-device, offline. Feasible today — every pipeline stage has a proven local counterpart.

  • VAD: Silero — already designed local in this repo
  • STT: faster-whisper on GPU/NPU
  • LLM: llama.cpp-class on-device models
  • TTS: Piper / Kokoro on-device voices
  • memory: sqlite-vec — a vector database in a file

The proof is structural: the demo you just ran uses stub providers through the exact same interfaces a local or cloud model would use. If the stubs work — and 28 tests say they do — the swap is an adapter, not a rebuild.

A NOTE FROM THE AUTHOR

This is my working prototype — active development continues. I have spent more than a decade working professionally with sound and voice, and VoiceRT is built on that experience: I know which processing belongs at every point of the chain, where automation pays off, and how this has to behave on a server.

I see it as one universal agent configurable for practically any domain: it is built to run locally, to speak multiple languages, and to expose the most convenient integration surface I could design — a stable frame contract and ~50-line adapters — with a fully local knowledge base as the next milestone.

In games it connects to audio middleware such as Wwise or FMOD: the engine routes the player's voice to the NPC, and the NPC talks back inside the game world — no dialogue scripts. And the strongest application is a personal assistant for a business owner, where the whole database, the reasoning, and the speech synthesis eventually live on the mobile device and work without internet. With a database, prepared prompts, and a voice — that is an engineering roadmap, not a wish.
