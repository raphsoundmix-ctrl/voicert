The shift

From dialogue trees to living characters.

Indie teams do not need another generic chatbot attached to an NPC. They need a system that preserves what makes the NPC theirs — while making interaction dramatically more flexible.

Traditional NPC voice

  • Every response must be authored and recorded.
  • Memory lives in game scripts, if it exists at all.
  • New languages multiply recording and QA work.
  • Changing a line means going back into production.

VoiceRT character layer

  • Author the character once; generate the interaction layer.
  • NPCs can remember player-specific context.
  • One voice performance can become a multilingual asset.
  • Role and lore constraints remain part of the runtime contract.
Character control

AI can improvise. The character does not.

The core idea is not “let an LLM do whatever it wants.” VoiceRT treats each NPC as a controlled character profile with an explicit contract.

Next: localization

One actor performance. Many languages.

Use an approved source performance to preserve voice identity and speaking characteristics across supported languages, instead of rebuilding the character from scratch for every localization.

01 / SOURCE

Start with the actor

Provide a high-quality source recording from an authorized voice actor. VoiceRT can use that performance as the reference for the character voice.

Voice likeness and cloning should only be used with the actor’s explicit rights, consent and applicable usage terms.

Built for game production

AI stays behind the engine boundary.

VoiceRT is designed as a runtime layer, not as a second game engine. The game owns world state, tools and audio routing. The AI owns interpretation, dialogue and voice generation.
